## What changed

- **Rename eval directories to current verbs.** `governance/evals/bootstrap/` → `init/`. `governance/evals/amend/` → `directive/`. The rename is a `git mv` — fixtures travel with their parent. Internal naming was the shallowest layer of fixture rot but the most visible: anyone reading `governance/evals/` saw verb names that no longer exist.
- **Move existing reset/ evals into uninstall/.** The old `governance/evals/reset/` carried evals that tested uninstall behavior (the prompts literally said "Remove every governance artifact"). The directory matched the current verb name but the contents matched a different verb. Moved verbatim into `governance/evals/uninstall/` with the README updated to reflect uninstall vocabulary. Fixture's AGENTS.md marker spelling refreshed from the legacy `<!-- governance: rules-to-follow -->` to the current paired `<!-- governance: directives-to-follow -->` (per UNINSTALL_FLOW.md Step 5's marker contract). New eval 4 covers soft mode preservation of seeded `QUALITY.md` / `COSTS.md`; the old hard-mode eval becomes eval 1.
- **New reset/ evals for restore-to-pinned semantics.** Five evals exercising the actual `governance reset` verb per RESET_FLOW.md: `--directive <id>` against a builtin-owned directive (eval 1), `--pack <id>` against a community pack with cache resolution (eval 2), `--all --dry-run` (eval 3), refuse-to-run when `.governance/packs.lock` is missing (eval 4), and `--all --drop-handauthored` (eval 5). New fixture `drifted-repo/` carries three packs in the lockfile — `governance-kit/core` (`source: builtin`), `acme/widgets@5f3c0a1b...` (`source: gh`), `acme/drifted-repo` (`source: local`) — with intentional drift in the first two (`# DRIFT:` comments) and a hand-authored team-policy directive in the third. New fixture `lockfile-missing/` exercises the lockfile-driven refuse path.
- **New pack/ evals for the six pack verbs.** Six evals exercising `pack {search,create,add,update,remove,list}` per PACK_VERBS.md. Eval 1 (`pack search`) reads the kit's `governance/assets/catalog.community.json`. Eval 2 (`pack create frontend`) scaffolds a hand-authored pack at `.governance/packs/<owner>/frontend/` with no `source:` field in `pack.yaml` and no lockfile mutation. Eval 3 (`pack add gh:acme/soc2-pack@main`) covers SHA pinning, capability check, diff-before-exec, and lockfile upsert. Eval 4 (`pack update`) covers SHA-drift detection and the silent skip of `builtin` / `local` entries. Eval 5 (`pack remove`) covers directive-folder deletion, constitution-subsection cleanup, lockfile removal, and `install_assets_seeded` pruning. Eval 6 (`pack list`) covers the unified `lock-list --long` table across all three sources. Two new fixtures: `seeded-repo/` (only `governance-kit/core`) and `repo-with-installed-pack/` (core + community + repo-local).
- **Refresh assertions to install.yaml + packs.lock + governance-kit/core.** Old assertions referenced the pre-#103 "installed-pack manifest" (singular) and used generic category names like "Foundation/Security" where the assertion was actually about pack provenance. New assertions in init/ check `.governance/install.yaml` v3 (with `owner:` + `repo:` + `hook_strategy:`), `.governance/packs.lock` v2 (with the `governance-kit/core` builtin entry), the AGENTS.md paired-marker block, and the line-2 `governance-kit:managed` ownership marker on `.githooks/*`. Old "installed-pack manifest" wording deleted across the board.
- **Add Step 5b lockfile-sync assertions to directive/ evals.** DIRECTIVE_AMEND_FLOW.md Step 5b mandates the lockfile mutate alongside the directive triple — added per-eval assertions that capture the verb-specific lockfile behavior: `add` upserts the local pack entry's `directives:` list (scaffolding `pack.yaml` + `lock-add` if no entry exists yet), `modify` is a lockfile no-op, `remove` drops the id (and removes the entry + `pack.yaml` if it was the last directive). New eval 6 exercises the upstream-pinned refusal path — modifying a `governance-kit/core` directive (`source: builtin`) is refused locally per Step 2's interaction-policy table.
- **Refresh fixture install pair to v3 / v2 schemas.** Existing directive fixtures (`seeded-repo/`, `repo-with-file-size-rule/`, `repo-with-console-log-rule/`) gained `.governance/install.yaml` (v3) + `.governance/packs.lock` (v2) so Step 5b assertions are exercisable. The `seeded-repo/` fixture additionally gained a `governance-kit/core` pack folder with a `secrets-hygiene` directive (so eval 6 has a `builtin`-owned directive to refuse on); its CONSTITUTION.md grew a matching subsection. Reset and pack fixtures ship the install pair from the start.
- **Update fixture AGENTS.md marker spelling.** Old fixture used `<!-- governance: rules-to-follow -->` (pre-PR-#26 marker). Refreshed to the current paired `<!-- governance: directives-to-follow -->` / `<!-- /governance: directives-to-follow -->` so the uninstall fixture exercises the paired-marker happy path that UNINSTALL_FLOW.md Step 5 prefers (the opening-marker-only heuristic is now reserved for legacy-marker fallback testing, which would need a separate fixture). Fixture body text refreshed to say "Uninstall should never touch this line" instead of "Reset should never touch this line".

## Out of scope

- **A `manifest-missing` fixture for uninstall/.** UNINSTALL_FLOW.md's `partial / heuristic` path is interesting (manifest absent but artifacts present, defaults to dry-run, requires explicit opt-in for destructive modes). A fixture for it would be a near-duplicate of `bootstrapped-repo/` minus the install pair. The four uninstall evals already cover the main shapes; the heuristic path can be added later if the verb gains coverage gaps.
- **Cache-state seeding for the pack/ evals.** Eval 3 (`pack add gh:acme/soc2-pack@main`) and eval 4 (`pack update`) need a populated `${GOVERNANCE_KIT_HOME:-~/.governance/cache}/packs/...` to exercise the offline-cache-hit path. The fixtures themselves are network-agnostic; the eval harness is responsible for seeding cache when needed. Punted because cache-seeding is a harness concern, not a fixture concern.
- **Native-test eval coverage.** NATIVE_TESTS.md describes the post-init opt-in path for porting bash directives to pytest / jest / go test. Evals for that flow would need pytest / jest fixtures, which is its own project. The current rewrite covers only the `governance` skill's bash-default surface.
- **Re-running each eval against the live skill.** Verifying assertions actually grade correctly against today's skill behavior is what the eval harness is for; this rewrite establishes the assertion set, not the pass/fail signal.
