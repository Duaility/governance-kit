## What changed

- Add `has_file_waiver` helper to `governance/assets/dot-governance/lib.sh` and dogfood `.governance/lib.sh` that scans the first 10 lines for `governance: allow-<directive> [<sub-check>] <reason>`. The helper takes `<file> <directive> [<sub-check>]` — when sub-check is provided, the pattern becomes `governance: allow-<directive> <sub-check>` (both tokens must appear together on the same line); when omitted, only `governance: allow-<directive>` is required (so future whole-directive file-level waivers fit the same shape). The implementation `head -n 10 "$file" | grep -q "$pattern"` keeps the cost bounded — even on a 10k-line file, only the first 10 lines are read. The same code lands at both layers (template + dogfood) verbatim; the dogfood file's line-2 `# governance-kit:managed kit-version=0.2 generated=2026-05-08` marker is preserved (the helper appends below `has_waiver`, not at the top).
- Wire `has_file_waiver` into the `file-size-limit` block of `packs/core/directives/repo-hygiene/check.sh` with sub-check token `file-size-limit`. The new line `has_file_waiver "$file" "repo-hygiene" "file-size-limit" && continue` sits between the file-existence guard and the `wc -l` line-count, so a waivered file is skipped before its size is even measured. Also amended the directive header docstring to flag the new escape hatch alongside the existing threshold tunable note (`GOVERNANCE_MAX_FILE_SIZE_MB` / `GOVERNANCE_FILE_SIZE_LIMIT`), so a future reader sees the per-file waiver in the same paragraph that describes the per-repo overrides.
- Update `packs/core/directives/repo-hygiene/constitution.md` to document the waiver inline and in the Exceptions clause. The directive subsection's `file-size-limit` bullet gains a trailing sentence "File-level waiver: `governance: allow-repo-hygiene file-size-limit <reason>` in the first 10 lines." The Exceptions paragraph now reads "The `debug-statements` sub-check supports line-level waivers ... The `file-size-limit` sub-check supports file-level waivers — place `governance: allow-repo-hygiene file-size-limit <reason>` in the first 10 lines of the file." The constitutional surface stays load-bearing: a future user / agent reading just the directive snippet sees both waiver shapes documented next to the rules they apply to.
- Extend `packs/core/directives/repo-hygiene/evals/test.sh` with a fail-without-waiver / pass-with-waiver pair against `GOVERNANCE_FILE_SIZE_LIMIT=10`. A 30-line `big.ts` file is staged, then `expect_fail` asserts the directive flags it under the lowered limit; the file is then rewritten with `// governance: allow-repo-hygiene file-size-limit refactor in #999` as the first line and `expect_pass` asserts the same content (now plus one waiver-comment line, total 31) is silently skipped. The `GOVERNANCE_FILE_SIZE_LIMIT=10` env override is per-call so the existing pass and fail cases keep using the directive's natural 500-line default. Eval results: `bash scripts/test-packs.sh` reports `1 pack(s), 14 directive(s), 14 eval(s) passed`.
- Sync the repo-level `CONSTITUTION.md` `### repo-hygiene` subsection and append an Evolution Log entry. The repo-level subsection's `file-size-limit` bullet and Exceptions paragraph mirror the pack constitution snippet edits verbatim (so the dogfood and the source-of-truth pack snippet stay byte-equivalent on the directive's policy text). A new Evolution Log entry dated 2026-05-08 names the downstream consumer that surfaced the gap, summarizes the helper + sub-check token shape, and explains why the sub-check is part of the waiver token (forward-compat with future file-level sub-checks).

## Out of scope

- Adding file-level waivers to the other sub-checks of `repo-hygiene`. `large-files` and `build-artifacts` operate on whole files but the right per-file carve-out for those is `git lfs track` / `.gitattributes` (large-files) or `.gitignore` / `_artifacts` denylist amendment (build-artifacts), not a head-of-file comment. `merge-markers` flags accidental conflict residue and a waiver would defeat the purpose. `debug-statements` already has line-level waivers. The new helper is reusable if a future sub-check legitimately wants file-level waivers — the sub-check token in the pattern keeps the namespace clean.
- A repo-config waiver mechanism (`.governance/exceptions.yaml`) — option (2) in the upstream issue. The head-of-file form is the simplest shape that's `git blame`-visible, doesn't need a parser, and matches the existing `governance: allow-*` family. A separate config file would split waivers across two locations and add a parse-and-validate step to every pack runner. Can revisit if the head-of-file form proves insufficient.
- Backfilling line-level waivers for `large-files` / `build-artifacts` (option 3 in the upstream issue, "per-line waiver on the final line"). The line-level waiver shape is for cases where a specific line in the file is the violation (a `console.log` call, a hardcoded secret); for whole-file violations the head-of-file marker is the natural form.
- Tightening the waiver token format (e.g. requiring an issue reference like `#NNN` in the reason). The reason string is free-form by convention across all `governance: allow-*` waivers; tightening just one sub-check's waiver would create an inconsistency. The reviewer's PR review remains the trust boundary on whether the reason is actually load-bearing.
- Updating fixture lib.sh copies under `governance/evals/*/files/*/.governance/lib.sh`. Those are point-in-time fixtures pinned to specific kit versions / scenarios (stale-repo, future-kit-repo, etc.) and updating them would invalidate the eval semantics they encode.
