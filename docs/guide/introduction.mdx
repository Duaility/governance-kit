# What is Governance Kit?

Governance Kit is a toolkit for **governance-driven development (GDD)**. Your repository's rules live in a versioned `CONSTITUTION.md`, every rule ships with an executable test, and agents do the work of keeping the repo compliant.

It installs as an [Agent Skill](https://agentskills.io) into Claude Code, Codex, Cursor, and 40+ skills-compatible runtimes. One skill, one entry point: the `governance` verb surface.

## What problem does it solve?

Coding agents often complete the task in a way that is locally fine and globally wrong. They land features through the wrong layer, revive patterns you retired, widen a boundary you wanted held, or half-follow `AGENTS.md` and miss the constraint that mattered. The objective passes; the repo drifts. The next agent has no memory of the correction, so you give it again.

Adding more prompt does not solve this at scale. Instruction files grow, context gets crowded, and the rule still reaches only the current session. OpenAI's [harness-engineering](https://openai.com/index/harness-engineering/) write-up describes the same failure set from running an agent-first codebase: instruction files that "rot instantly", agents that replicate uneven patterns until the codebase drifts, knowledge trapped in chat threads, and human QA capacity becoming the bottleneck.

Two things stop scaling at agent throughput:

1. **Steering.** Your guidance has to reach the *next* agent, on the *next* branch, without you in the room. Per-turn prompting doesn't compose: the next agent can't read your last conversation.
2. **Visibility.** When agents ship the diffs, you need a readable trail, not a stack of PRs and ephemeral chat transcripts.

Governance Kit answers both with repo-native artifacts:

- **A constitution**: `CONSTITUTION.md`, a versioned set of directives every agent reads and every commit is checked against.
- **Receipts and ledgers**: per-issue receipts (with cost and steering accounting) and the `QUALITY.md` board, recording what agents were told, what they did, and what it cost.

## How does the loop work?

The repo carries the durable instruction; the agent reconciles reality against it.

> Describe the state, continuously check reality, and let agents reconcile the difference.

A failed check is a *gap report*. It names the directive, the offending file and line, and the rationale. A capable agent can use that rationale to handle cases the rule's author never encoded. This follows the [harness-engineering](https://openai.com/index/harness-engineering/) principle that coherence comes from executable rails around the agent, not ever-larger instruction blobs.

The design applies the declarative reconciliation model used by Kubernetes and Terraform to a repository:

| | In Governance Kit |
|---|---|
| **Desired state** | `CONSTITUTION.md`: directives, rationale, exceptions, evolution log |
| **Current state** | the working tree, staged diff, commit message, receipts |
| **Controller** | `.governance/run.sh` + git hook dispatchers + CI |
| **Reconciler** | the agent: reads the gap and its rationale, fixes the repo, re-runs |

## How deep can a rule go?

The useful distinction is the depth of invariant you can express. Start with deterministic checks; escalate only when the rule genuinely needs context or judgment. One rule layer carries all four depths:

| Depth | What you can say | How it runs |
|---|---|---|
| **Repo state** | "Every repo needs a README, a license, a security contact, an architecture note." | Cheap `check.sh` over the tree, locally and in CI. |
| **Change set** | "A CI-config change needs a reason in the commit." "A receipt for issue #42 must name the files this PR changed." | Diff-aware hooks plus CI's merge-base walk. |
| **Ledger** | "For each agent-authored change, show the issue, receipt, token cost, and steering count." | Receipt accounting rows, cross-checked by directives. |
| **Sub-agent attestation** | "Before merging a cross-layer refactor, have a fresh reader compare the diff to the architecture map." | The hook fails with a fresh-context sub-agent prompt; the agent records a PASS/REFUTED section; the hook verifies it is there. |

The failures that hurt are rarely mechanical, such as forgetting the formatter. They are semantic, and no single enforcement style catches both kinds. Governance Kit matches each rule to a surface: cheap deterministic checks for mechanical rules and [fresh-context attestation](https://github.com/Duaility/governance-kit/blob/main/kit/references/SUBAGENT_ATTESTATION.md) for judgment calls.

## What a directive looks like

Every directive is a self-contained folder: test, prose, metadata, and fixtures travel together:

```
internal-doc-links/
├── directive.yaml    # category, summary, surface, hook
├── check.sh          # the executable test (pre-commit + CI)
├── constitution.md   # Directive / Rationale / Enforced by / Exceptions
└── evals/test.sh     # pass + fail fixtures
```

The `constitution.md` carries the *why*:

```markdown
### internal-doc-links

- **Directive**: Every relative-path markdown link resolves to a real file;
  opt in to also require every doc stay reachable from a declared root.
- **Rationale**: A broken link rots silently: the doc still renders but lies,
  and an agent that follows it bails.
- **Enforced by**: .governance/packs/governance-kit/foundation/directives/internal-doc-links/check.sh
- **Exceptions**: Line-level waiver on the broken-link line.
```

A bare check would only confirm that the links point somewhere. The rationale tells the next agent and human why a connected documentation graph matters.

## What it is not

<AccordionGroup>
  <Accordion title="Not a linter" icon="paintbrush">
    Formatting opinions belong in formatters. Directives encode *governance*: invariants whose violation costs you an incident, an audit finding, or institutional memory.
  </Accordion>
  <Accordion title="Not a spec tool" icon="file-text">
    [spec-kit](https://github.com/github/spec-kit)-style workflows answer *"what should this feature do?"* for a specific task before implementation. GDD answers *"what must every commit satisfy?"* with persistent, post-implementation checks. They compose: spec-kit steers the agent at runtime; GDD steers it at "compile time."
  </Accordion>
  <Accordion title="Not just hooks" icon="git-branch">
    pre-commit / husky / lefthook run scripts. Governance Kit also carries the rationale, audit trail, and evolution history alongside each test. Its checks are plain bash, so you can extract them if you only want enforcement.
  </Accordion>
</AccordionGroup>
