# The runtime: hooks & run.sh

You type `git commit`, and a directive either fires or it doesn't — but it's worth knowing what runs in that gap before you trust it to gate your work. This page traces what actually happens between `git commit` and `[PASS]`: the runner, the generated hook dispatchers, and the enforcement contract with CI.

## The pieces

```
.governance/
├── run.sh        # entrypoint: discovers and runs every installed check
├── lib.sh        # shared helpers: directive_start/_end, violation, has_waiver, …
├── install.yaml  # init receipt (choices + side effects)
├── packs.lock    # pack pin state
└── packs/<owner>/<name>/directives/<id>/check.sh   # the vendored checks

.githooks/        # generated dispatchers (Path A; or .husky/, .governance/hooks/)
├── pre-commit
├── commit-msg
├── prepare-commit-msg
├── post-commit
└── pre-push

.github/workflows/governance.yml   # CI: bash .governance/run.sh on every PR
```

`run.sh` and `lib.sh` are **kit-owned, version-stamped files**: line 2 carries `# governance-kit:managed kit-version=<v>`. That marker is the ownership contract — it is how `kit update` knows what it may regenerate and how `uninstall` knows what it may delete. Files without the marker are yours; the kit never touches them.

## What happens on `git commit`

<Steps>
  <Step title="git fires a hook">
    `core.hooksPath` points at `.githooks/`, so git runs the generated dispatcher (e.g. `pre-commit`, then `commit-msg`).
  </Step>
  <Step title="The dispatcher filters by hook kind">
    Each installed directive declared its `hook:` in `directive.yaml`; the pre-commit dispatcher runs only pre-commit directives, the commit-msg dispatcher only commit-msg ones.
  </Step>
  <Step title="Populators run first">
    Directives can ship side-effect scripts (`hooks/<kind>.sh`) — the audit
    session-identity helper writes an explicit harness/session row into the
    issue receipt before Git snapshots the tree. Remediation writes;
    governance reads; the two are separate scripts.
  </Step>
  <Step title="Identity signals stay explicit">
    Session identity uses environment signals or a kit-owned sidecar supplied by
    the runtime. The hook does not inspect chat transcripts, session databases,
    usage files, or harness-private paths.
  </Step>
  <Step title="Each check runs">
    `check.sh` sources `lib.sh`, announces itself with `directive_start`, inspects the repo (staged tree for `change-set` directives, tree-at-rest for `repo-state` ones), records `violation`s, and `directive_end` decides pass/fail.
  </Step>
  <Step title="Any failure blocks the commit">
    It prints the directive id, the offending location, and the message. The agent fixes and retries.
  </Step>
  <Step title="CI repeats everything on the trunk">
    `governance.yml` runs `bash .governance/run.sh` on every PR and push to main — full suite, no hook filtering, no skip.
  </Step>
</Steps>

Run it yourself any time:

```sh
bash .governance/run.sh                    # full suite
bash .governance/run.sh <directive-id>     # one directive
```

## Generated, not copied: the hook dispatchers

`init` does not ship static hook files — it **generates** dispatchers from the installed manifest, for one of three strategies:

| Strategy | When | Where dispatchers land |
|---|---|---|
| `githooks` (Path A, default) | No tracked hook framework detected | `.githooks/`, plus `git config core.hooksPath .githooks` and a committed `scripts/enable-governance.sh` for new clones |
| `husky` (Path B) | Repo already uses husky | `.husky/` |
| `pre-commit` (Path B) | Repo already uses pre-commit.com | `.governance/hooks/`, referenced from `.pre-commit-config.yaml` |

All five dispatcher kinds are generated with identical bodies and the line-2 ownership marker. Because they're generated from `directive.yaml` declarations, installing or removing a directive just regenerates them — there is no hand-maintained hook registry to drift.

<Note>
**Collisions are first-class.** If a hook already exists at a managed path, `init` stops and offers: **wrap** (rename yours to `<name>.userhook`, exec it at the end of the dispatcher — the default), **merge by hand** (skip hook install, rely on CI), or **overwrite with backup**. `uninstall` reverses the wrap, renaming your hook back.
</Note>

## The enforcement contract

Local hooks are a convenience; **CI is the contract**:

- `SKIP_GOVERNANCE=1` and `--no-verify` skip the local hook for hotfixes — but `governance.yml` re-runs every directive on every PR, and there is no developer-side bypass for CI.
- **No network at commit time.** Hooks and checks never fetch; all fetching lives inside user-invoked verbs. A flaky hook is a skipped hook, and a skipped hook silently demotes enforcement to CI-only — so the hook path is kept deterministic and fast (checks target < 1 second each).
- **Deterministic verdicts.** Same repo state, same result — checks avoid wall-clock and randomness so re-runs are meaningful.
- **bash + git, nothing else.** Everything on the commit path — `run.sh`, `lib.sh`, every `check.sh`, and every `hooks/*.sh` — is bash and POSIX awk. No python, no package manager, no toolchain to install — governance-kit holds itself to that with its own repo-local `no-commit-path-python` directive, so the guarantee is enforced where the commit path is authored rather than left to each consumer to re-check. A commit hook that needs an interpreter the contributor doesn't have is a hook that silently stops enforcing.

## Session identity is the only runtime contract

The audit pack does not maintain a harness adapter registry. The
`agent-session-identity` hook records a `date | harness | session` row when a
runtime explicitly supplies those values through supported environment signals
or a kit-owned identity sidecar.

The contract is intentionally narrow: no transcript, session database, usage
file, or harness-private path is opened. If a runtime does not expose a stable
session identifier, the hook records `-`; if no runtime is present, it no-ops.
Adding support for a new harness means exporting a generic identity signal, not
adding a vendor-specific reader to governance-kit.

Judging remains separate: a directive's `judge.cmd` can name a fresh-context
sub-agent or shell command, and receives only declared repository artifacts.
There is no adapter indirection and no usage/cost measurement lane.
## Mode B: validating history, not just the working tree

`change-set` directives that police *commits* (message format, receipt touches, ledger shape) have two operating modes:

- **Pending-commit mode** (in the hook) — validate the commit being made right now.
- **Walker mode** (in CI) — walk the commits between the merge-base and `HEAD`, validating each. This is what makes the rules hold on the trunk even when a local hook was skipped. The audit-chain links are built to survive squash-merges without a walker re-validation step: the commit↔issue anchor is the receipt path (which the squash preserves), and the session identity lives in the frozen receipt rather than in commit trailers — see [the audit chain](/concepts/audit-chain).
