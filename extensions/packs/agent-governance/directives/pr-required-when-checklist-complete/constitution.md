### pr-required-when-checklist-complete

- **Directive**: When HEAD carries a tracked `receipts/*.md` whose `## Checklist` section has at least one `- [x]` item and zero `- [ ]` items (i.e. the work is fully done by the agent's own attestation), and the current branch is not `main` / `master`, an open pull request must exist for the current branch on the GitHub remote. The directive reads HEAD content (not the working tree), so the commit that *completes* the checklist lands without being blocked — the gate fires on the next commit attempt or in CI, whichever comes first.
- **Rationale**: The receipt's `## Checklist` (required by `receipt-per-issue`) is the agent's mechanical signal for "I am done." Without a directive that *acts on* that signal, the checklist becomes a self-report no one consumes — the work sits on a feature branch waiting to be noticed. Gating the next commit (and CI) on PR existence makes the workflow's natural next step ("open a PR for review") a hard requirement rather than a habit. The gate is shaped as a check, not an action: governance-kit directives describe invariants on tree state, not side effects on remote systems. The agent (or the developer) opens the PR with `gh pr create --fill`; the directive only verifies one is there. Reading HEAD rather than the working tree is what makes the gate ergonomic — the commit that ticks the last box lands successfully, and the dev/agent then opens the PR before their next commit.
- **Enforced by**: `tests/governance/directives/pr-required-when-checklist-complete/check.sh`
- **Exceptions**: Skip-with-warning when the GitHub CLI (`gh`) is not installed or not authenticated — local developers without `gh` are not blocked, but CI environments (where `gh` is expected) will enforce. When `gh` is present but the `gh pr list` call fails, the directive fails (network or API issues should not silently bypass the gate). The directive is also a no-op on `main` / `master` and when no commits exist yet.
