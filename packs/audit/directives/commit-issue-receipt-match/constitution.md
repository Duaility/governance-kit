### commit-issue-receipt-match

- **Directive**: Every completed change set adds or modifies at least one `receipts/issue-<N>.md`. The touched receipt's filename **is** the change's issue anchor. Intermediate commits on a feature branch do not each need a receipt edit. A completed change is a pull-request aggregate (`merge-base..HEAD` in CI) or a commit made directly on the default branch (where no PR boundary exists). Merge and revert commits are exempt.
- **Rationale**: Traceability belongs at the completed-change boundary (issue #370), not as per-commit receipt-touch bookkeeping. File-first (issue #293) still survives squash: the receipt path sits in the aggregate diff identically before and after a squash-merge. `commit-message-format` independently requires the subject `(#N)`; `receipt-per-issue` independently validates uniqueness and completed-change evidence — including that a session-only stub cannot satisfy that evidence. This directive supplies the remaining link: the completed change is associated with a receipt file. Provenance stamping may still update a receipt on intermediate commits without counting as completion.
- **Enforced by**: `.governance/packs/governance-kit/audit/directives/commit-issue-receipt-match/check.sh` — Mode A (commit-msg) requires a receipt only for a pending commit on the default branch; Mode B (CI / `run.sh`) requires a receipt somewhere in the aggregate `base..HEAD` diff, not in each commit.
- **Exceptions**: Merge commits (parent count > 1 in Mode B; the commit-msg hook never sees them) and revert commits (subject starts with `Revert "`) are exempt. Per-commit/change-set waiver — `governance: allow-commit-issue-receipt-match <reason>` in the commit body (Mode A) or in any commit of the change set (Mode B). Reason required. Use for release commits and unusual cross-cutting refactors that legitimately touch no receipt.
