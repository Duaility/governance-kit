### stdlib-only-python

- **Directive**: Every tracked `.py` file under `.governance/` imports only modules on the effective Python standard-library allowlist, judged by each top-level (zero-indent) `import X` / `from X import ...` statement's root module. Relative imports (`from . import x`) are always allowed.
- **Rationale**: Issue #355 locks the product's dependency posture: the kit's own tooling needs nothing but a bare `python3` — no `pip install`, no venv, no lockfile. A single third-party import (`import requests`, `import yaml`) silently breaks every consumer who hasn't separately provisioned that package, and often there's no signal until the script actually runs — which for kit tooling like the sweep workflow can be well off the commit path, days after the import landed.
- **Enforced by**: `.governance/packs/governance-kit/foundation/directives/stdlib-only-python/check.sh` (runs in `pre-commit`).
- **Exceptions**: The effective allowlist is the sibling `defaults.conf` (a generous stdlib list, pack-owned and refreshed on `pack update`) layered with the user overlay `.governance/conf/governance-kit/foundation/stdlib-only-python.conf` — a bare line adds an allowed root module, `!<module>` removes one of the shipped defaults. An import nested inside a function or class body is out of scope by design (only top-level imports are parsed). Marked `recommended: false` and shipped only in the `strict` preset.
