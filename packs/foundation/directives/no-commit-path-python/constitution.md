### no-commit-path-python

- **Directive**: No tracked file on the consumer commit path — `.governance/lib.sh`, `.governance/run.sh`, `.governance/runtimes/*.sh`, every installed directive's `check.sh` / `hooks/*.sh` / `runtimes/*.sh` under `.governance/packs/*/*/directives/*/`, and every `.githooks/*` dispatcher — contains a non-comment line invoking `python` or `python3`.
- **Rationale**: Issue #355 locks the product's dependency posture: a consumer repo needs nothing but bash + git to commit. Python is fine for the kit's own tooling off the commit path (lifecycle verbs, sweep — see the sibling `stdlib-only-python` directive), but a `python3` call sitting on the hook every commit runs through means a consumer without `python3` on `PATH` gets a broken hook the first time they clone the repo, silently, with no signal until the pre-commit dispatcher errors out. The commit path is the one place absoluteness pays for itself — everyone commits, not everyone runs `governance update` or the sweep workflow.
- **Enforced by**: `.governance/packs/governance-kit/foundation/directives/no-commit-path-python/check.sh` (runs in `pre-commit`).
- **Exceptions**: Path-glob waivers live in the sibling `defaults.conf` (empty by default) layered with the user overlay `.governance/conf/governance-kit/foundation/no-commit-path-python.conf` — a bare line exempts a path from the scan, `!<path-glob>` un-exempts one of the (currently empty) shipped defaults. Use this for a knowingly-opted-out community pack, never to launder a new violation. Marked `recommended: false` and shipped only in the `strict` preset — repos that install a pre-#355 community pack with a python `check.sh` need to see that as an actionable failure to fix, not a baseline everyone inherits unasked.
