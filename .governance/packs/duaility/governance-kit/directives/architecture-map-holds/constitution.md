### architecture-map-holds

- **Directive**: (Repo-local dogfood directive.) `ARCHITECTURE.md` carries this repo's layer / responsibility model as a Mermaid `flowchart` block — the **skill** installs the **kit**, the kit consumes the **packs**, arrows point only downward — and that block must not drift from the real tree. The check asserts: (1) exactly one non-empty `mermaid` fenced block exists and declares a `flowchart`; (2) every path token tagged for the check (an `arch-map-path:` HTML comment beside the block) resolves to a real path **and** appears verbatim inside the block, so renaming a layer without updating the map fails the build; (3) the boundary edges the picture asserts hold — `skill/` carries no kit version string and contains nothing but `SKILL.md` and `bootstrap.py` (installer carries no kit code), the repo pins both axes (`.governance/install.yaml` has a non-empty `kit_version`, `.governance/packs.lock` lists at least one pack), and the diagram carries the two downward edges (`skill → kit`, `kit → packs`) with no upward edge.
- **Rationale**: A responsibility map is exactly the kind of architecture knowledge a static analyzer can't derive from imports (issue #271's bucket 2) — but every node here is a real directory with a boundary rule the kit already enforces, so the picture can be made a *gate* rather than a decoration. Without it, the diagram is prose: it rots silently the first time `skill/`, `kit/`, or `packs/` is renamed, or the first time installer code leaks into `skill/`, and a reader trusts a map that no longer matches the tree. Folding the cheap, high-value checks (named paths resolve; the one-way layering survives; the thin-skill boundary the #198 split established stays clean) into the diagram's own commit makes the visual self-certifying — it fails CI when the layering drifts instead of misleading the next reader. The analogy text (rustup ≈ skill, …) and "the kit hardcodes no pack version" stay audit-only (issue #271 bucket 3): they're prose claims whose mechanical form is false-positive-prone (docs and examples legitimately mention pinned pack tags), so gating them would only breed waivers.
- **Enforced by**: `.governance/packs/duaility/governance-kit/directives/architecture-map-holds/check.sh` (repo-state; CI/run.sh) and `.githooks/pre-commit`.
- **Exceptions**: None. The map is meant to be kept current — if the tree changed, update the Mermaid block and the `arch-map-path:` tags in the same change. This directive describes governance-kit's own installer/product/content layering and is meaningless in any consumer repo, so it lives in the repo-local `duaility/governance-kit` pack and never ships in a bundled `packs/*` concern pack.
