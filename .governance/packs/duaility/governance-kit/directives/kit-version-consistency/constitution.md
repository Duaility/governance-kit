### kit-version-consistency

- **Directive**: (Repo-local dogfood directive.) The governance-kit source tree's kit-version stamps and the kit/pack axis invariant must agree: `kit/assets/kit.yaml` carries the kit version, and every bundled `packs/<pack>/pack.yaml`'s `min_governance_kit` is `<=` that version. `kit.yaml` is the single source of truth for the kit axis. The published skill (`skill/`) versions independently — it carries no kit code and no kit version (issue #198), so its frontmatter is out of this directive's scope.
- **Rationale**: The shipped `kit-version-sync` directive validates an *installed* repo (manifest vs managed-file markers), but the kit's authoring sources — `kit.yaml`, each concern pack's floor — only exist in this repo and have no manifest to check against. Without this directive, a bundled pack could declare a floor newer than the kit it ships in, and nothing would catch it until a consumer hit the `packctl validate-pack` rejection. This directive holds the kit's own version story to the same "every rule has a test" bar the kit demands of everyone else.
- **Enforced by**: `.governance/packs/duaility/governance-kit/directives/kit-version-consistency/check.sh` (repo-state; CI/run.sh) and `.githooks/pre-commit`.
- **Exceptions**: None. The repair path is `scripts/release.sh`, which bumps `kit.yaml` in one `chore(release)` commit. See `kit/references/VERSIONING.md`.
