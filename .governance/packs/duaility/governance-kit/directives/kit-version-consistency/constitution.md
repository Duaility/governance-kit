### kit-version-consistency

- **Directive**: (Repo-local dogfood directive.) The governance-kit source tree's kit-version stamps and the kit/pack axis invariant must agree: `governance/assets/kit.yaml`'s `version` equals `governance/SKILL.md`'s frontmatter `version`, and `packs/core/pack.yaml`'s `min_governance_kit` is `<=` the kit version. `kit.yaml` is the single source of truth for the kit axis; `SKILL.md`'s version is a derived copy that `scripts/release.sh` re-stamps.
- **Rationale**: The shipped `version-consistency` directive validates an *installed* repo (manifest vs managed-file markers), but the kit's authoring sources — `kit.yaml`, the skill frontmatter, the core pack's floor — only exist in this repo and have no manifest to check against. Without this directive, the source of truth and its skill-frontmatter copy could drift, or a core pack could declare a floor newer than the kit it ships in, and nothing would catch it until a consumer hit the `packctl validate-pack` rejection. This directive holds the kit's own version story to the same "every rule has a test" bar the kit demands of everyone else.
- **Enforced by**: `.governance/packs/duaility/governance-kit/directives/kit-version-consistency/check.sh` (repo-state; CI/run.sh) and `.githooks/pre-commit`.
- **Exceptions**: None. The repair path is `scripts/release.sh`, which bumps `kit.yaml` and re-derives the `SKILL.md` stamp from it in one `chore(release)` commit. See `governance/references/VERSIONING.md`.
