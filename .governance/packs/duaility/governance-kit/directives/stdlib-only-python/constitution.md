### stdlib-only-python

- **Directive**: (Repo-local dogfood directive.) Every tracked `.py` file this repo *ships* — `kit/**/*.py` (the lifecycle engines under `kit/assets/packs/lib/` and anything else inside the kit artifact) plus `skill/*.py` (the published bootstrap shim) — imports only modules on the effective Python standard-library allowlist, judged by each top-level (zero-indent) `import X` / `from X import ...` statement's root module. Two kinds of import are first-party and always allowed: a relative import (`from . import x`), and a flat sibling import whose root resolves to a `.py` file or package directory next to the importing file — how the kit's engines reference each other.
- **Rationale**: Issue #355 locks the product's dependency posture — the kit's own tooling needs nothing but a bare `python3`: no `pip install`, no venv, no lockfile — and Q11 of that issue is explicit that *the kit should hold itself to it as a directive*. A single third-party import (`import requests`, `import yaml`) silently breaks every consumer who hasn't separately provisioned that package, and often there's no signal until the script actually runs, which for kit tooling like the lifecycle verbs under `kit/assets/packs/lib/` can be well off the commit path — a consumer's first `pack update` or `directive add` — days after the import landed. This repo's own test harness under `scripts/**` is deliberately out of scope: it never ships to a consumer, so the same issue's lane table leaves it unconstrained. The vendored `.governance/` tree is out of scope too — it is materialized from the *last release* and lags `kit/` by one cycle by design.
- **Enforced by**: `.governance/packs/duaility/governance-kit/directives/stdlib-only-python/check.sh` (repo-state; CI/run.sh) and `.githooks/pre-commit`.
- **Exceptions**: The effective allowlist is the sibling `defaults.conf` (a generous stdlib list) layered with the overlay `.governance/conf/duaility/governance-kit/stdlib-only-python.conf` — a bare line adds an allowed root module, `!<module>` removes one of the defaults. An import nested inside a function or class body is out of scope by design (only top-level imports are parsed), as is a `from`-line whose module token is not a dotted identifier — that is prose inside a module docstring, not an import.
